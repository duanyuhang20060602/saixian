# HDMI1.4b_Transmitter_v3.0：单板原 GIF 增量播放

本版用于 HX4S20C / EG4S20BG256 单板动图验证。输出 1280×720，原 GIF 的 480×480 画面放在 (400,120)，周围填黑。企鹅、奖杯、MVP 文字及运动均取自用户选择的第四个素材，没有重新设计动作。颜色转换成 RGB565，增量编码对转换后的像素无损。没有轮播、音乐和双板 1080p 功能。

## 下载上板

1. 备份测试 TF 卡，把交付包中的 `TROPHY.DLT` 复制到卡中。本版沿用按物理扇区寻找文件头的读取方式，需要整个文件连续存储，不解析 FAT 簇链；普通复制到使用过的卡不保证连续。扫描范围为前 512 MiB，并设有 240 秒扫描超时。仅准备新的 .DLT 素材，避免卡上残留多份同格式数据。工程不自动格式化或写入 TF 卡。
2. 安全弹出 TF 卡，开发板断电时插入，HDMI 接 **HDMI_A**，接好供电和 JTAG 下载器。SW1、SW2 先置 0。
3. 打开 TD 的 `Tools → BitWriter`，点 `Refresh` 检测 EG4S20，选择 **Program SRAM**。
4. 移除 BitWriter 列表里的旧文件条目，点 `Add` 选择 **HDMI1.4b_Transmitter_v3.0_QuadWrite.bit**，点 `Run`。这个专用文件名用于区分上一版 ReadAlign；内容与本次工程的标准名称位流一致。
5. 上电先显示独立于 TF/SDRAM 的转圈画面。至少显示 96 个视频帧（约 1.58 秒），同时完成 TF 初始化、扫描、整包 CRC 校验、内存检查和首帧解码。首帧准备好后在视频帧边界显示，额外停留约 1 秒，随后接着播放原动图。失败时继续显示转圈画面并给出错误码。SW1=1 暂停，SW1=0 继续；SW2=0 显示正常错误码，SW2=1 显示诊断数据，KEY1 每按一次切换一页。

Program SRAM 是临时配置，断电后需要重新下载，不能据重新上电后的旧 Flash 画面判断本版效果。下载成功后不要按 PROGRAM_B。先用 SRAM 验证显示和连续播放，再决定固化到 Flash。

LED 输出定义：LED1=可显示帧已提交；LED2=TF 初始化成功；LED3=HDMI HPD；LED4=TF/数据/解码/显示欠载错误。数码管显示 Ehh：E11=TF 初始化超时，E13=扫描未找到素材或扫描超时，E14=扇区截断/读取超时，E15=TF 读入流 CRC 错误，E16=输入/FIFO 异常；E26/E27/E28=内存访问异常，E29=SDRAM 缓存读回 CRC 错误；E39=增量解码异常；E3B=索引起始地址异常，E3C=编码长度异常，E3D=编码数据越过文件边界，E3E=帧时长异常；E40=视频欠载。旧位流使用笼统的 E3A；本版拆分了索引错误。

TF 初始化阶段 d0..d4：0=等待 CMD0，1=等待 CMD8，2=等待 CMD55/ACMD41，3=进入 CMD16，4=就绪。板上物理显示顺序与文字读法反向时，A3E4d 对应 d4 E3A。七段编码器不生成字母 R。出现故障时记录转圈是否可见、四个 LED、数码管完整显示和等待时间。

## 四字写入接口修正版

ReadAlign 版已在实板通过缓存检查：预期、上传接口、SDRAM 读回三个载荷 CRC 都为 `EA54DD20`，但仍报 `d4 E39`，没有出现首帧。重新核对官方 APUG011 文档后，确认旧任意地址单字补丁不符合四字分组规则。

本版改为四字对齐事务，未修改位置使用 `1111` 掩码，实际补丁使用 `0000`；同组连续补丁合并，解码完成等待写入排空后才允许显示。TF 素材不用重新复制。SDRAM 仍为 50 MHz，移相从 8 ns（144°）提前到 7 ns（126°）以增加读采样裕量；HDMI/TF 频率不变。2026-10-10 用户上板反馈“效果非常好”；图样与 CRC 检查全部保留。依据见 `安路资料复核.md`，独立 3.0Project 内为 `doc/安路资料复核.md`。

### 新增解码诊断

每个描述符先完整读取并校验编码 CRC，再读取进行解码；完成时再校验实际消耗流的 CRC。错误时禁止提交首帧或新帧。

| 错误码 | 含义 | 自动页 |
| --- | --- | --- |
| E31 | 命令计数为零 | 6..b |
| E32 | 保留命令类型 11 | 6..b |
| E33 | 超过帧内剩余像素对数量 | 6..b |
| E34 | literal 需要的数据超过编码剩余字数 | 6..b |
| E35 | fill 缺少颜色字 | 6..b |
| E36 | 编码结束，帧游标没有到 115200 | 6..b |
| E37 | 解码前编码流 CRC 错误 | 0..5 |
| E38 | 解码消耗流 CRC 错误 | 0..5 |

以上解码错误的页定义：0/1=预期编码 CRC，2/3=解码前实际编码 CRC，4/5=解码消耗流 CRC，6/7=出错命令，8/9=编码流内零起始字偏移，A/b=帧内像素对游标。每对页先低 16 位、再高 16 位。若解码中途停止，消耗流 CRC 仅代表前缀，不能直接与整段比较。这里是编码流 CRC，不能与整包载荷 CRC 混淆。内存错误仍使用下节原有页定义。

## 保留的读回对齐诊断

上一版 IndexFix 已在实板显示 `d4 E29`；后续 CacheDiag 显示 `d4 E2d`（E2D），同时用户报告 SW2 置 1 没有效果。E2D 表示上传接口载荷 CRC 通过，但直接写读图样呈现提前一个 32 位字的特征。它不能单独区分写侧错位与读侧数据/有效信号错位，也不能证明 SDRAM 芯片损坏。

此前 ReadAlign 版验证“读回数据早于有效信号一拍”的假设：在 50 MHz 内存时钟每拍捕获读回数据，保持原有效信号，使用上一拍捕获值送入仲裁器。首字出现有效信号之前也必须捕获，不能只在有效时采样。仿真先用提前一拍的数据模型复现原来的 E2D，再用捕获电路验证图样、完整测试载荷 CRC 和命令 FIFO 字序。实际控制器仍为加密 IP；ReadAlign 在实板通过图样和完整缓存 CRC，但仍未显示首帧。用户已反馈本 QuadWrite 版效果良好；旧故障的具体因果关系仍未独立确认；保留 CRC 和 TF 素材；本版相位修正按前节说明执行。图样或整包 CRC 失败时仍禁止播放。

为了应对 SW2 无法切换的现象，故障时增加自动显示：先保持正常 `d4 Ehh` 约 5 秒，再每秒切换一个诊断页，共 6 页，之后回到错误码并重复。不需要拨 SW2 或按 KEY1。E2B..E2F 自动显示 6..b 页（实际数据、预期数据、地址）；解码错误按前节表格选择自动页；其余错误显示 0..5 页（CRC）。如果 SW2 手动模式能够工作，它仍可优先用于逐页查看；目前开关无响应的原因未确认。

| 错误码 | 本版检查结果 |
| --- | --- |
| E2A | 实际送入 SDRAM 写接口的数据 CRC 已与文件头不符，先查上传 FIFO、打包和跨时钟路径 |
| E2B | 已知 64 字图样写入、读回不一致，且不属于下面的特殊情况 |
| E2C | 图样读回比预期晚一个 32 位字；首字不参与偏移判别 |
| E2D | 图样读回比预期早一个 32 位字；末字不参与偏移判别 |
| E2E | 图样读回全零 |
| E2F | 图样读回全一 |
| E29 | 上传接口 CRC 和 64 字图样通过，但整包读回载荷 CRC 仍失败 |

E2C/E2D 是图样特征判别，尚不能单独确定是读侧还是写侧错位。上述结果用于缩小排查范围，不作为芯片故障结论。

故障后可置 SW2=1。数码管最左一位是页号，中间空一位，右边四位是十六进制数据。KEY1 每按一次前进一页，长按只前进一次。每个 32 位值按低 16 位、再高 16 位显示，记录后用“高位+低位”拼接。

| 页号 | 数据 |
| --- | --- |
| 0 / 1 | 文件头预期载荷 CRC，低 / 高 |
| 2 / 3 | 上传写接口实际载荷 CRC，低 / 高 |
| 4 / 5 | 整包读回实际载荷 CRC，低 / 高；若检查未开始，其值为 0 |
| 6 / 7 | 图样首个不匹配的实际数据，低 / 高 |
| 8 / 9 | 同位置预期数据，低 / 高 |
| A / b | 首个不匹配位置的绝对 SDRAM 字地址，低 / 高 |

SW2=0 时显示上述自动循环，手动页号复位为 0。若仍是 E29，记录自动出现的 0..5 页；若是 E2B/E2C/E2D，记录 6..b 页。诊断显示只读取寄存器，不控制播放或内存总线。

## 数据和内存

- `TROPHY.DLT`：1,890,304 字节；原 GIF 27 帧、每帧 40 ms。
- 原始逐帧 RGB565 数据：12,441,600 字节；本包约为其 15.19%。
- 原 GIF 文件为 602,406 字节。这个自定义格式为 FPGA 简化解码，压缩率低于 GIF；存储节省是相对于逐帧 RGB565 数据而言。
- 首帧完整编码，后续使用跳过不变像素、复制字面量像素和重复像素命令，另存一条末帧回首帧的增量。
- 启动时把整个压缩包预载 SDRAM，此后播放不反复读 TF。两块解码帧缓存共 921,600 字节，包与缓存共占 2,811,904 字节，小于板上的 8 MiB SDRAM。
- TF 读入流 CRC 通过后，先校验上传写接口 CRC，再进行直接写读图样检查，最后完整读回 SDRAM 中的包校验载荷 CRC。全部通过后才允许解析索引或显示首帧。
- 图样检查使用已上传包的头部前 64 个字作为临时区域。头部元数据已单独锁存，后续解码不读取这 64 字；载荷 CRC 和索引均从第 128 字开始。不会修改 TF 文件，也不覆盖帧缓存、索引或动画命令。
- SDRAM 索引/命令读取统一使用 64 字对齐的物理突发；仲裁器过滤前缀和填充，只向解码 FIFO 发送实际需要的数据。8 字索引、1 字空变化帧和跨界请求都遵循此规则。
- 修改非显示缓存后，在视频帧边界切换；随后把同一增量重放到另一缓存，使两块缓存同步。
- HDMI 使用已有 75 MHz 像素时钟和 375 MHz 串行时钟，1650×750 栅格约为 60.606 Hz。40 ms 的 GIF 切换时刻取下一个视频帧边界，单帧时长会有刷新量化，动作序列和整体目标速度保持原 GIF。

## 编译与验证

`build.ps1` 将工程复制到 `E:/Codex/Work/saixian_delta_build`，使用本机 TD 6.2.168116 构建。只发布新生成且布线建立、保持时序均通过的位流。`tools/finalize_release.py` 检查源码、位流、报告与构建快照一致，并生成交付包。GUI 工程名为 `HDMI1.4b_Transmitter_v3.0.al`，顶层 `top`。

先安装/使用已有 Pillow，运行 `tests/run_tests.py` 准备数据并检查全部 27 帧、循环回首帧、双缓存、畸形命令以及 TF 扇区/CRC/截断/超时。`tests/run_pipeline.py` 使用原版 FIFO 和真实视频栅格验证前四次显示及像素输出。`tests/run_budget.py` 使用十拍 SDRAM 响应及四字突发/掩码检查模型和按真实栅格生成的读带宽需求，检查完整循环、暂停恢复及准备时限。`tests/tb_axis.v` 检查 HDMI 数据适配器像素和帧/行标记。

`tests/run_boot_tests.py` 检查无 TF 时的转圈输出、首帧提交、黑边、动画后续提交、首次停留时间以及故障代码。原播放链路的全部帧解码、加载和带宽基线见相应日志；启动流程的新增逻辑单独测试。

`tests/run_cache.py` 使用原版命令 FIFO 检查对齐物理读取、索引前缀过滤、短尾流、跨边界逻辑流、完整读回 CRC、上传损坏，以及全零、全一、前后错一字、其他图样损坏注入；另用原版异步上传 FIFO 的 100/50 MHz 时钟验证 4096 字的多次指针回绕、上传与读回 CRC 和上传损坏定位。`tb_index` 区分地址、长度、边界和时长四种索引错误。

这些仿真不包含加密 SDRAM 控制器和 HDMI 物理层的实际硬件行为；TD 时序通过不能代替上板结果。启动版在实板显示转圈和 d4 E3A；IndexFix 版显示 d4 E29；CacheDiag 版显示 d4 E2D，仍无首帧。根因尚未确认。ReadAlign 已通过缓存 CRC，但首帧报 E39。2026-10-10 用户反馈本 QuadWrite 版“效果非常好”，硬件状态记为 user-reported-pass；未进行独立长时间实板测量。完整循环与原版 FIFO/真实栅格回归已更新为四字写入、字节掩码、十拍读响应及编码 CRC 检查。
