# V3.1 切图后持续白条：SDRAM 刷新保护修复

用户于 2026-10-18 明确症状：切图后，新图片一直保留白条。该症状与单帧显示欠载不同，需检查缓存内容是否在写入时受损。

## 发现的接口缺陷

A/B 两板的 `frame_fifo_read.v`、`frame_fifo_write.v` 都接入了 `Sdr_init_ref_vld`，但原代码没有使用它。安路 APUG011 v1.2 的 §2.3、§3 要求在刷新标志释放后开始读写。原状态机可能在刷新期间继续输出命令，并同时弹出写 FIFO、递增地址和计数。刷新期间不被存储器接收的写入会变成缓存中的缺字，之后每帧重复显示同一损坏图片。

## 修改

- A/B 两板的读写突发均在刷新期间暂停准入。
- 实际 `App_rd_en` / `App_wr_en` 出口也受刷新信号保护，覆盖“已准入、寄存器尚未发出首字”这段启动窗口。
- FIFO 弹出、地址、突发计数均沿用实际命令使能；刷新期间一起保持，释放后从同一字继续。
- 没有增加读响应计数等待，也没有修改板间 ready/valid 握手，避免混入此前启动回归的两项变更。
- A 板显示 FIFO 仍为 1024 字、后台写准入预留仍为 768 字。896 字尝试导致预取几乎停滞；832 字虽通过理想带宽模型，也不能修复已写坏的图片，因此没有保留门限试调。

## 仿真证据

`tests/tb_frame_refresh.v` 使用实际生产读写状态机和异步 FIFO，刷新仅在命令空闲边界开始，持续 20 周期。模型在刷新期间不接收读写命令，并检查完整目标缓存内容，覆盖 RGB565、RGB888、并行显示读和后台写。

| 模块 | 无刷新保护的对照 | 修正后 |
|---|---|---|
| A / RGB565 | 80 个目标字损坏 | 2560 个写入字、2560 个读出字全部一致 |
| A / RGB888 | 298 个目标字损坏 | 3840 个写入字、3840 个读出字全部一致 |
| B / RGB565 | 80 个目标字损坏 | 2560 个写入字、2560 个读出字全部一致 |
| B / RGB888 | 282 个目标字损坏 | 3840 个写入字、3840 个读出字全部一致 |

重现命令：`python tools/test_frame_refresh.py --board a` 和 `--board b`。对照源码由脚本从当前代码仅移除刷新保护生成；结果与源码 SHA256 保存在 `tests/results/board_*_frame_refresh_results.json`。

首次加载（尚未显示）场景也通过 RGB565/RGB888 写入完整性检查，未采用等待读响应计数的启动机制。

完整 720p RGB888 压力模型另增加每约 765 周期一次的 20 周期刷新：完整读出 691200 字、显示读空 0 次，同时产生 52579 字后台预取；1079 个刷新窗口内读写命令均为 0。结果与源码 SHA256 见 `tests/results/rgb888_refresh_results.json`、`rgb888_refresh_bandwidth.log`。

上述证明接口缺陷已在模型中修正，尚不能代替真实 SDRAM 控制器和上板画面的验收。位流硬件状态仍为待复验。

## 上板

使用同名 `WHITEBAR_REFRESH_FIX` 的 A/B 配套位流，两个板都重新加载后再切换到高精度模式。重新加载会清空旧缓存并重新接收图片；原先已经写坏的缓存不会被新逻辑自动修补。连续手动切图、等待图片静止、再验证自动轮播。
