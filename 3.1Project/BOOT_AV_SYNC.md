# V3.1：图片与音乐同步启动

本版基于已完成 FFT 频谱、双声道波形和音频修复移植的 V3.1。保留原来的黑底加载动画，
不增加新的动画段。本次不改变最多五首音乐的登记上限；“不限定音频数量”按用户澄清解释为
只等待第一首音乐就绪，无需等待全部音频扫描结束。

## 启动顺序

1. A 板显示黑底光点、“LOADING”和进度条；B 板加载图片并查找音乐。
2. 发现首首音乐后，B 板继续原有处理并传给 A。A 缓存至少 512 个立体声采样，保持输出静音，
   保留第一条待播放采样，不提前消耗曲目内容。
3. 首张图片、音乐缓冲和动画最低显示时间全部就绪后，加载画面在视频消隐期退出。
4. 第一帧正式画面开始时放行音频，下一次 48 kHz 采样时刻开始输出缓存内容，间隔最多约
   20.8 微秒。音频处理自身保留既有的 32 采样对齐延迟；显示器内部延迟不由 FPGA 控制。

音乐一旦缓冲好，即使 B 板仍在扫描其它曲目，也能完成启动。
如果扫描完成且确认无音乐文件，则不等待音频缓冲，正常显示图片。
确认“无音乐”所需时间取决于原有 TF 扫描范围、数据位置和读取速度。
发现音乐但持续无法缓冲时保持加载动画，避免错误地将“仍在加载”当成“没有音乐”。

## 动画

沿用无需 TF 素材的 FPGA 生成动画：黑色背景、八个蓝色光点、LOADING 文字及分阶段平滑进度条。
最低显示 90 帧，约 1.49 秒；首帧和音频缓冲连续就绪后，在消隐期一次性退出。
等待音乐时仍显示加载动画，进度条不会提前完成。普通切图和音乐切换不会重播开机动画。

## 协议及使用

B 板在音频 SPI 状态字预留 bit 15 回报扫描完成状态；音频格式、128 采样包大小、采样率、
音量和修复算法保持原样。因此 A、B 应成套烧录本目录 delivery 中的 BOOT_AV_SYNC 位流。
TF 图片、音乐、AWARD720.DLT 及现有按键操作保持。

## 验证

`python tools/test_boot_audio_sync.py` 使用实际 A/B SPI 和音频处理模块验证：
加载期静音、首采样保留、未扫完全部目录即可启动、首帧放行、无音乐卡退出。
同时重跑既有的 1280 采样双板音频传输回归。
结果见 `tests/results/boot_audio_sync_results.json` 和 `tests/results/audio_port_results.json`。
其余 FFT、波形、音频修复和奖杯逻辑继承上一版，已有测试证据随包保留。

最终资源、建立/保持时间余量和源文件 SHA256 见 delivery 内两板 manifest。
本同步启动版本仍需实板确认显示器上的实际声音和画面。

本次最终结果：A 板 LUT 10256、寄存器 9083、9K RAM 57、32K RAM 12、DSP 17；
B 板 LUT 10650、寄存器 7621、9K RAM 43、32K RAM 12、DSP 9。
A 建立/保持余量分别 +0.122/+0.022 ns，B 分别 +0.102/+0.021 ns，全部时序总负余量为零。
A 板使用 seed 16 完成布局，物理重试记录见 `delivery/board_a_reseed.json`；
其重新构建的默认 seed 也已设为 16，时钟约束保持原样。
